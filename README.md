# 온타임 — 완성본에서 시작하는 예약 서비스 공부

브라우저에서 사용하는 1:1 상담 예약·대기 웹서비스입니다.
프런트엔드만 흉내 낸 화면이 아니라 API, 인증, SQL 데이터베이스가 연결된 학습용 첫 버전입니다.

## 사용 방법

1. 사이트에 ChatGPT 계정으로 로그인합니다.
2. 달력에서 날짜를 선택하고 시간을 고릅니다.
3. 예약자가 없다면 예약 확정, 있다면 대기로 등록됩니다.
4. 내 예약·대기에서 확정 상태와 대기 순번을 확인합니다.
5. 시작 전 예약·대기를 취소할 수 있습니다. 예약 취소 시 다음 대기자가 자동 확정됩니다.
6. 관리자는 날짜별 예약자·대기자를 조회하고, 새 시간을 추가하거나 접수를 마감할 수 있습니다.

모든 예약 시간은 한국 시간입니다. 30분 단위로 운영합니다. 처음 접속하면 내일부터 14일간 예약 시간을 만듭니다. 이후 시간은 관리자가 추가합니다.
접수 마감은 새 신청을 막는 기능입니다. 기존 신청과 취소 시 대기 승격은 유지됩니다.
로그인은 Sites가 제공하는 ChatGPT 인증을 사용합니다. 별도 이메일·비밀번호 가입은 구현하지 않았습니다.
첫 배포는 소유자만 접근 가능한 비공개입니다. 이 상태에서 처음 로그인한 사용자를 관리자로 저장합니다. 사이트를 다른 사람과 공유하더라도 그 뒤 가입한 사용자는 일반 회원이 됩니다.

## 기술 구조

화면: React + TypeScript
서버: Vinext API route + Cloudflare Workers
DB: Cloudflare D1 (SQLite 계열 SQL)
스키마·마이그레이션: Drizzle
인증·배포: Sites

앞서 설명한 PostgreSQL FOR UPDATE 방식과는 구현이 다릅니다. D1은 PostgreSQL이 아니므로 같은 잠금 SQL을 사용하지 않습니다. 대신 하나의 신청 테이블과 DB가 부여하는 순서로 예약·대기를 통합해 구현했습니다.

```text
사용자
  → app/booking-app.tsx: 화면과 버튼
  → POST /api/booking: 신청 요청
  → app/api/booking/route.ts: 로그인·시간·권한 검사
  → D1: SQL로 신청을 한 번에 저장
  → GET /api/booking: 현재 순번 조회
  → 내 예약 화면
```

## 파일 읽는 순서

| 순서 | 파일 | 무엇을 볼까 |
| --- | --- | --- |
| 1 | app/page.tsx | 홈페이지가 어떤 컴포넌트를 보여 주는지 |
| 2 | app/booking-app.tsx | load(), act(), 날짜·시간 선택, 내 예약, 관리자 화면 |
| 3 | app/api/booking/route.ts | GET과 POST가 어떤 요청을 처리하는지 |
| 4 | db/schema.ts | 테이블, 기본 키, 외래 키, 인덱스 |
| 5 | drizzle/0000_ambiguous_smiling_tiger.sql | 실제 DB 생성 SQL |
| 6 | app/chatgpt-auth.ts | 로그인한 사용자를 서버에서 확인하는 과정 |
| 7 | scripts/test-booking.mjs | 동시 요청과 권한을 어떻게 검증하는지 |
| 8 | app/globals.css | 데스크톱과 모바일 배치 |

처음부터 CSS나 설정을 전부 읽지 않아도 됩니다. 화면에서 예약 한 번을 실행하고, act → POST의 join → INSERT → GET의 mine → status 순서로 따라가세요.

## DB 구조

```text
members (회원)
  id: 로그인 계정의 사이트별 고유 ID
  name, email: 표시용 정보
  role: admin / member

slots (예약 시간)
  id: 날짜_시간
  date: YYYY-MM-DD
  time: HH:mm
  open: 접수 가능 1 / 마감 0

entries (예약과 대기를 합친 신청)
  id: DB가 자동으로 부여하는 접수 순서
  slot_id: 신청한 시간
  user_id: 신청한 회원
  active: 유효 1 / 취소 0
  created_at: 신청 시각 (DB의 UTC 값)
```

members 1 → N entries, slots 1 → N entries 관계입니다.

## 중복 예약은 어떻게 막을까?

이 서비스는 예약과 대기를 별도 저장하지 않고 하나의 줄로 다룹니다.
한 시간대에서 active=1인 신청 중 id가 가장 작은 한 명만 예약자입니다. 뒤에 있는 사람은 대기자입니다.

```text
id 101 / 민수 / active 1 / 순번 1 → 예약 확정
id 102 / 지연 / active 1 / 순번 2 → 대기 1번
id 103 / 수진 / active 1 / 순번 3 → 대기 2번
```

민수가 취소하면 101의 active를 0으로 바꿉니다.
현재 유효한 신청의 맨 앞은 102가 되므로 지연이 예약자가 됩니다. 별도 승격 작업이나 타이머가 필요하지 않습니다.

핵심 규칙:

- 신청 순서는 요청을 보낸 기기 시간이 아니라 DB의 ID로 확정합니다. 거의 동시에 누른 두 요청 중 DB에서 먼저 저장된 요청이 앞섭니다.
- 마감·시간 검사를 INSERT ... SELECT 문 안에서 처리합니다. 조회 후 저장 사이의 틈을 만들지 않습니다.
- 같은 회원이 같은 시간에 두 번 유효 신청할 수 없도록 부분 UNIQUE 인덱스를 둡니다.
- 취소와 대기 승격은 하나의 active 갱신과 동일한 순번 규칙으로 이루어집니다.
- 다른 시간대는 별도 줄입니다. 담당자 한 명, 시간당 한 명이라는 첫 버전의 가정입니다.
- 대기 목록을 건너뛰어 예약하는 별도 경로를 만들지 않습니다.
- 모든 SQL 값은 bind로 전달해 문자열 조립에 의한 SQL 주입을 방지합니다.

순번 계산 SQL을 찾아 읽어보세요:

```sql
SELECT COUNT(*)
FROM entries q
WHERE q.slot_id = e.slot_id
  AND q.active = 1
  AND q.id <= e.id;
```

내 앞과 나 자신을 세므로 결과 1은 예약자, 결과 2는 대기 1번입니다.
이 구조는 1명 정원의 고정 슬롯에 맞습니다. 가변 길이 예약의 시간 겹침, 여러 담당자, 다인 정원은 별도 설계가 필요합니다.

## API 목록

모든 작업은 /api/booking을 사용합니다. 조회 결과는 캐시하지 않습니다.

| 메서드 | action | 요청 값 | 처리 |
| --- | --- | --- | --- |
| GET | 없음 | 없음 | 내 정보, 시간 목록, 내 신청, 관리자만 전체 신청 |
| POST | join | slotId | 예약 또는 대기 신청 |
| POST | cancel | id | 시작 전 본인 신청 취소 |
| POST | create | date, time | 관리자만 새 시간 추가 |
| POST | toggle | slotId | 관리자만 접수 열기·마감 |

인증되지 않은 변경 요청은 401, 권한 부족·다른 출처의 변경 요청은 403, 잘못된 날짜는 400, 중복 신청·마감된 시간 등은 409입니다.
화면에서 관리자 버튼을 감추는 것 외에 서버에서도 권한을 확인합니다.
이름과 이메일은 사용자 표시용이며, 예약 소유권은 계정 ID로 판단합니다.

## 내 컴퓨터에서 실행

Node.js 22.13 이상과 npm이 필요합니다. PowerShell에서 소스 폴더로 이동한 뒤 실행하세요.

```powershell
npm run install:ci
npm run build
node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0000_ambiguous_smiling_tiger.sql
npm run dev -- --port 5173
```

브라우저에서 http://127.0.0.1:5173/ 를 엽니다.
로컬 로그인은 Seedy라는 개발용 계정입니다. 배포하면 실제 ChatGPT 로그인을 사용합니다.
마이그레이션 SQL은 비어 있는 로컬 DB에 한 번만 적용합니다. 테이블이 이미 있다면 다시 실행하지 마세요.
로컬 DB와 배포 DB는 별개입니다. 로컬 테스트 내역이 배포 DB로 복사되지 않습니다.
DB는 브라우저 저장소가 아니라 서버에 저장합니다. 서버에 요청이 성공했다면 페이지를 새로고침해도 기록이 유지됩니다.

```powershell
node node_modules/typescript/bin/tsc --noEmit

```

동시성 통합 테스트는 dev 서버를 종료하고 배포 빌드를 로컬에서 실행해 확인합니다.

```powershell
npm start -- --port 5174
```

다른 터미널에서:

```powershell
node scripts/test-booking.mjs
```

테스트는 루프백 주소에만 요청합니다. 로컬 배포 Worker에만 테스트 계정 헤더를 보내며, 운영 사이트의 인증을 우회하지 않습니다.
테스트용 첫 관리자는 local_seedy입니다. 로컬 dev에서 한 번 로그인한 뒤 실행하면 됩니다.
20명이 같은 시간에 신청했을 때 예약자 1명·대기자 19명, 중복 신청, 타인 취소 차단, 자동 승격, 재신청 시 맨 뒤, 접수 마감, 관리자 권한, 미인증 요청, 출처 검증, 날짜 검증을 확인합니다.
테스트에서 만든 신청만 취소합니다. 테스트 회원·시간·취소 이력은 로컬 DB에 남습니다.
Windows 로컬 Worker가 재시작 중이면 서버가 준비된 후 다시 실행하세요.

## 탑다운 학습 실습

### 1. 화면에서 요청 찾기

브라우저 개발자 도구의 Network를 열고 예약합니다.
/api/booking POST의 요청 JSON과 응답 JSON을 확인합니다.
질문: 버튼 클릭만으로 DB에 저장할 수 있을까요? 왜 서버가 필요할까요?

### 2. 예약 버튼부터 SQL까지

booking-app.tsx에서 action: 'join'을 찾습니다.
route.ts에서 b.action === 'join'과 INSERT 문을 찾습니다.
질문: 로그인한 회원 ID를 화면이 보내지 않고 서버에서 가져오는 이유는 뭘까요?

### 3. 순번을 눈으로 계산하기

entries의 예시 세 줄로 순번 COUNT SQL을 손으로 계산합니다.
가장 앞선 행의 active를 0으로 바꾼 뒤 다시 계산합니다.
질문: 예약 상태를 따로 UPDATE하지 않아도 승격되는 이유는 뭘까요?

### 4. 제약의 필요성 실험하기

로컬 복사본에서 one_active_entry 인덱스의 역할을 살펴봅니다.
같은 사용자가 동시에 10번 신청하면 어떤 값이 저장되는지 테스트 코드에서 확인합니다.
질문: 버튼을 비활성화하는 것만으로 중복 신청을 막을 수 있을까요?

### 5. 작은 기능 직접 바꾸기

첫 과제: 안내 문구와 색상을 바꿔보세요.
두 번째: 기본 예약 시간에 17:00을 추가하세요. 기존 DB 시간은 관리자에서 추가할 수 있습니다.
세 번째: 회원 1명이 보유할 수 있는 다가오는 예약 수를 제한해 보세요. UI와 서버 양쪽에 규칙이 필요합니다.
네 번째: 대기 승격 알림 기록을 저장하는 테이블을 설계해 보세요.

## 첫 버전의 범위

실제 구현: 로그인·로그아웃, 영구 저장, 예약, 취소, 대기, 자동 승격, 관리자 시간 추가·접수 제어, 반응형 화면, 15초 갱신.
추후 확장: 독립적인 이메일 가입, 결제, 문자·이메일 알림, 여러 담당자·지점, 운영 감사 로그, 대규모 트래픽 최적화.
자동 확정 알림을 외부로 보내지 않으므로 현재 결과는 내 예약에서 확인합니다.
비공개 배포 상태에서는 여러 실제 계정의 공동 접속이 제한됩니다. 다중 사용자 테스트는 격리된 로컬 Worker에서 검증했습니다.
'학습용 첫 버전 완성'은 모든 상업 운영 기능을 갖췄다는 뜻이 아닙니다.
